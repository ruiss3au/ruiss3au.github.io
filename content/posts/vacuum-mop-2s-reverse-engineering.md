We obtained root on our Xiaomi Vacuum-Mop 2S through its voice-download handler, then built a browser controller and inspected its cloud traffic. The experiments ran in October 2026 on model `ijai.vacuum.v19`, firmware `4.3.3_0081`. The entry point required authenticated local access. Our results establish command execution and a root shell on that unit and firmware; they do not establish an unauthenticated attack or behavior across other models.

We first needed a working local protocol. Discovery identified the robot but returned an unusable placeholder token. An owner-authenticated account workflow eventually supplied the per-device token. That credential had a different role from the account login: it authenticated local miIO requests. We tested it with one batch of ten property reads, checking response identifiers and token-dependent checksums. Battery, operating state, suction and other readings returned successfully. The declared device schema supplied names and capabilities, without proving every advertised action worked locally.

Next, we acquired the exact matching firmware from the vendor's download service and checked its length and checksum against the supplied metadata. We extracted the filesystem offline. The package included the key material needed to unlock its encrypted root filesystem, allowing us to inspect the shipped programs. This established access to the firmware contents, without testing modified-image acceptance or bypassing secure boot. We flashed no firmware.

The voice-download action accepted three strings: a target language, a download address and a purported checksum. Static analysis traced them through request parsing into a download worker in `RobotApp`. Local protocol authentication occurred before this path. Authentication therefore limited who could invoke the handler, while leaving the handler responsible for treating authenticated input safely.

The critical transition occurred when the handler constructed archive-extraction commands. It used the language string as part of a filename and directory, embedded those paths unquoted in shell text, and passed that text to `popen`. That function executes through a shell. Shell punctuation in an input field could consequently change how the command was parsed. The request's checksum field was copied and logged but was not compared on this path. A later archive-content check also accepted a missing checksum-list file. Neither check protected the earlier shell-command construction.

We tested reachability before command execution. A benign request caused the robot to fetch a lab-hosted file over plain Hypertext Transfer Protocol (HTTP). A second, short language string included a command that connected back to a bounded lab listener. We observed two connections from the robot, 18 milliseconds apart, matching the two predicted command-construction sites. Subsequent authenticated status queries succeeded. These observations turned a static shell-injection finding into demonstrated execution.

The firmware startup scripts suggested that `RobotApp` inherited root privileges, but we confirmed identity separately. We used the download path to stage a small setup script and an authorized public key, then invoked the script through the understood injection. A writable directory temporarily mounted over the read-only root home made key authentication possible, and the shipped Secure Shell (SSH) server provided access. The resulting session returned user identifier zero. Process inspection also confirmed that `RobotApp` ran as root.

Getting there exposed several mistaken assumptions. The installed archive utility sanitized traversal paths, so an attempted path-traversal route failed. The handler's own command prefix consumed the first segment of an early runner, changing its working-directory behavior. A debug flag persisted, but the temporary mount supplying authorized keys disappeared on reboot. Root SSH therefore required re-establishment after a restart. We had a working bridge, without boot-persistent key access. Static buffer-overflow candidates remained untested because shell injection already supplied the needed execution primitive.

We used the access to build a browser controller with server-side credentials and a fixed set of permitted actions. The backend ran on the lab host and was available through private remote access. Native manual steering supplied a useful protection: a 500-millisecond direction watchdog. Holding a browser button had to renew movement frequently enough to keep it active, while release, lost focus, or a hidden page had to end the hold.

Our first transport could await a reply long enough to miss that watchdog deadline. The fix sent fresh direction renewals every 200 milliseconds while a reply remained pending, with generation checks preventing an old hold from restarting after Stop. A separate browser lease expired when renewals ceased. A regression test introduced 720-millisecond replies and checked continued renewals, cancellation and immediate Stop. Hardware holds and subsequent owner use confirmed the corrected behavior in the recorded runs.

Steering also started suction because the vendor implemented manual movement as manual cleaning. A low suction setting still ran the blower. We traced the fan control and found that a path named `rpm`, suggesting revolutions per minute, represented commanded output rather than measured rotation. Repeatedly writing zero would race the native control loop. We instead held the original attribute open and temporarily mounted a private ordinary file over that single pathname, absorbing the vendor's commands while retaining access to the real output.

The guard required zero output before movement, a host lease and an independent device-side heartbeat timeout. Stop preceded restoration; uncertain cleanup blocked further movement or cleaning. In hardware tests, wheel counters changed while fan-pulse samples remained constant, and removing the override restored native fan operation. Brushes retained vendor behavior. These were bounded tests of suction suppression, without prolonged endurance testing or a claim that every cleaning actuator was disabled.

The light detection and ranging (lidar) preview needed its own evidence of freshness. Native display traffic exposed map and pose information, but manual mode did not reliably provide changing scans. We read a known observation buffer through SSH, validating executable identity, process lifetime, readable mappings and vector bounds. Concurrent changes triggered retries. Only a changing device timestamp made a scan fresh; fetching the same memory again did not reset its age. The browser showed robot-relative ranges without presenting them as a globally localized map.

We gave lidar power a separate lease, so preview could continue after steering stopped. Its remote helper restored owned power after heartbeat loss. Recorded tests showed changing scan timestamps and independent timeout restoration. The controller also gained a soundboard: recordings used the browser device's microphone and played through the robot speaker. This established no robot microphone. Silencing the exact Stop prompt also silenced ordinary cleaning-stop confirmations, a wider effect we documented. Tablet feedback later received reserved layout space because changing status text had moved a steering button during holds.

With local control working, we turned to the cloud. Connection destinations alone could identify infrastructure, but could not reveal encrypted contents. We found two separate Transport Layer Security (TLS) implementations. `RobotApp` used libcurl and a certificate file for uploads; `miio_client` used statically linked mbedTLS and a provider-supplied trust anchor for the persistent relay connection. Replacing one certificate file could not expose both channels.

An initial bounded logging window attributed actual property reports and storage-address requests to cloud dispatch. A later relay experiment went further: a hash-guarded staged copy of the client temporarily used a short-lived audit certificate authority and routed only its cloud TLS connection through our proxy. Peer verification and the expected peer name remained enforced on both sides, and device authentication remained intact. Heartbeats and an independent maximum duration bounded the override; the original executable remained underneath the temporary mount.

The decrypted reconnect and idle traffic included account and device identifiers, model and version fields, Wi-Fi network and access-point identifiers, signal information, local network addressing, memory and uptime diagnostics, network counters and property updates. A private equality check showed that a transmitted token matched the locally stored miIO access token. These values normally travelled inside TLS. Our controlled trust change exposed them for inspection; the observation was not evidence of plaintext transmission on the network. No password field appeared in this short capture, which could not establish what happens in every operating state.

A separate upload capture exposed map content. We decoded its body through Base64, Advanced Encryption Standard (AES) decryption, hexadecimal decoding, zlib decompression and Protocol Buffers parsing. The derived key depended on local device and account identifiers. Valid padding, a complete compressed stream and structured fields corroborated the decode. The result contained a nonuniform 640,000-byte grid, current-pose, charger and navigation fields, and a nonempty room-label field. We kept labels, coordinates, identity inputs and raw captures private.

That map request returned HTTP 403. Its bytes left the robot and passed through the proxy, but we did not establish successful storage, retention or deletion. It also used a separate object-storage endpoint rather than demonstrating map transfer inside the relay session. Firmware serializers supported cleaning-history and per-room preferences, but our stationary captures did not establish actual cleaning-event uploads. Generic schema fields likewise could not prove that this model collected images or audio.

We closed the audit by checking restoration: the original client hash, original trust files, direct cloud connectivity and a healthy controller were present in the final records. Audit listeners and temporary overrides were removed, and an earlier host redirect was cleaned up. Those checks describe the end of the experiments, without asserting a continuously monitored state.

Local control was demonstrated, but local-only operation remained unproven. We had not enforced internet blocking and exercised cleaning, docking, maps and reboot under that restriction. That experiment would also need to examine queued traffic after reconnection. Root access gave us tools to ask those questions; answering them required further observations beyond a working browser interface.
