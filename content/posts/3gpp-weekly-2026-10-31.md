Release 20 mobility work is trying to remove a limitation of earlier fast cell switching: the network can prepare a device to change its main serving cell, but the earlier framework cannot use that same switch command to control activation of the target's secondary cells. Apple's revised work-item description identifies that limitation and proposes dynamic activation as part of the switch. The October requests from Radio Access Network Working Group 2 (RAN2) concern the measurements and device capabilities needed to make it work. [RP-260232](https://www.3gpp.org/ftp/tsg_ran/TSG_RAN/TSGR_111/Docs/RP-260232.zip), [R4-2630009](https://www.3gpp.org/ftp/tsg_ran/WG4_Radio/TSGR4_121/Docs/R4-2630009.zip), [R4-2630011](https://www.3gpp.org/ftp/tsg_ran/WG4_Radio/TSGR4_121/Docs/R4-2630011.zip).

The work item connects this limitation to carrier aggregation: the target cell may already have supplied a configuration for additional carriers, but the switch command cannot dynamically choose their activation. Preparing the special-cell switch and preparing the secondary cells are related tasks, but they do not automatically complete together. The proposed improvement gives the network a way to select secondary-cell activation at the time of the switch, rather than simply accepting the carrier-aggregation configuration supplied earlier. [RP-260232](https://www.3gpp.org/ftp/tsg_ran/TSG_RAN/TSGR_111/Docs/RP-260232.zip).

## Fast switching starts with work done beforehand

Layer 1/Layer 2 Triggered Mobility (LTM) was introduced in Release 18 to reduce handover interruption and latency. The revised work-item description says Release 19 extended it across central units and added event-triggered Layer 2 reporting and channel-state information reference signals. These changes expanded the framework, but retained an important dependency: candidate cells provide configurations, and the serving cell assembles the configuration delivered to the device through radio resource control (RRC) signaling. [RP-260232](https://www.3gpp.org/ftp/tsg_ran/TSG_RAN/TSGR_111/Docs/RP-260232.zip).

That arrangement moves preparation ahead of the switch. The device already holds candidate configurations when it receives the lower-layer instruction to change cells. However, a change in a candidate's configuration can require renewed coordination between network nodes and another composition of the device's RRC configuration. The work-item justification singles out beam configuration and measurement across candidate cells as a source of frequent changes. [RP-260232](https://www.3gpp.org/ftp/tsg_ran/TSG_RAN/TSGR_111/Docs/RP-260232.zip).

The resulting tradeoff is between a fast switch and the work required to keep its prepared configurations usable. A short switch command does not eliminate coordination; it relies on that coordination having happened earlier. If configurations change often, the preparation process can itself become expensive. This is the architectural problem behind the Release 20 proposal to select among previously supplied measurement configurations using a control element at the medium access control layer (MAC CE). [RP-260232](https://www.3gpp.org/ftp/tsg_ran/TSG_RAN/TSGR_111/Docs/RP-260232.zip).

## Choosing a configuration is different from rebuilding it

The proposed dynamic measurement change is deliberately limited. The work item calls for MAC CE selection among prior RRC configurations of Layer 1 measurement and reporting. It does not describe arbitrary creation of a new configuration in the switch command. The network first provisions alternatives, then selects one that the device already knows. [RP-260232](https://www.3gpp.org/ftp/tsg_ran/TSG_RAN/TSGR_111/Docs/RP-260232.zip).

For example, suppose the network has already supplied two measurement configurations for candidate cells. Selecting the second configuration through a MAC CE would avoid sending that configuration again through RRC at the point of selection. This is an illustration of the work item's proposed mechanism, not a measured latency result. The initial provisioning remains necessary, and an alternative outside the prepared set would still be outside that selection mechanism. [RP-260232](https://www.3gpp.org/ftp/tsg_ran/TSG_RAN/TSGR_111/Docs/RP-260232.zip).

Secondary-cell activation is a separate objective in the same work item. It calls for the network to trigger activation as part of the special-cell LTM switch and to reuse candidate-cell measurement and reporting procedures where possible. It explicitly excludes early channel-state information acquisition for the secondary cell. The scope therefore supports coordinated switching and activation, without promising that every step needed to use an additional carrier has been eliminated. [RP-260232](https://www.3gpp.org/ftp/tsg_ran/TSG_RAN/TSGR_111/Docs/RP-260232.zip).

## A deactivated candidate still needs to be measurable

RAN2's October liaison asks Radio Access Network Working Group 4 (RAN4) to confirm that a device can send Layer 1 measurement reports for a configured LTM candidate secondary cell regardless of whether that cell is currently deactivated. The request preserves a distinction between a cell's activation state and its role as a measurement candidate. RAN2 states its understanding and asks for a radio-requirements check; the letter contains no RAN4 response. [R4-2630011](https://www.3gpp.org/ftp/tsg_ran/WG4_Radio/TSGR4_121/Docs/R4-2630011.zip).

If measurements can be obtained while a candidate is deactivated, the network can use those reports in deciding which prepared secondary cells to activate during a switch. Requiring activation before obtaining the relevant report would introduce an ordering dependency that the proposed combined operation would have to accommodate. This is a consequence of reading the measurement request against the work item's activation objective, rather than a new procedure specified in the liaison. [R4-2630011](https://www.3gpp.org/ftp/tsg_ran/WG4_Radio/TSGR4_121/Docs/R4-2630011.zip), [RP-260232](https://www.3gpp.org/ftp/tsg_ran/TSG_RAN/TSGR_111/Docs/RP-260232.zip).

The letter does not establish measurement freshness, reporting delay or an activation-time guarantee. Those details determine whether an available report is useful when the switch occurs. The work item assigns RAN4 the task of evaluating and specifying requirements as necessary; that requirement work cannot be replaced by a protocol group's statement that reporting is expected to work. [R4-2630011](https://www.3gpp.org/ftp/tsg_ran/WG4_Radio/TSGR4_121/Docs/R4-2630011.zip), [RP-260232](https://www.3gpp.org/ftp/tsg_ran/TSG_RAN/TSGR_111/Docs/RP-260232.zip).

## Capability reuse has to cover the expanded operation

The companion October liaison asks Radio Access Network Working Group 1 (RAN1) and RAN4 to confirm reuse of relevant Release 18 and Release 19 LTM device capabilities. RAN2 explains why it needs confirmation: the candidate-cell scope now includes both candidate special cells and candidate secondary cells. It also says some capabilities remain under discussion. The request concerns whether the earlier capabilities cover the expanded use, rather than assuming that support for special-cell switching also covers secondary-cell activation. [R4-2630009](https://www.3gpp.org/ftp/tsg_ran/WG4_Radio/TSGR4_121/Docs/R4-2630009.zip).

The dependency runs in both directions. A switch command that can activate secondary cells is useful only if the network has enough information to choose them. Measurements of candidate cells are useful only if the configuration and device capabilities let the network act on them. Reading the work-item description alongside the October liaisons, the open problem is whether Release 20 can connect those steps without adding a separate configuration exchange to each switch. [RP-260232](https://www.3gpp.org/ftp/tsg_ran/TSG_RAN/TSGR_111/Docs/RP-260232.zip), [R4-2630009](https://www.3gpp.org/ftp/tsg_ran/WG4_Radio/TSGR4_121/Docs/R4-2630009.zip), [R4-2630011](https://www.3gpp.org/ftp/tsg_ran/WG4_Radio/TSGR4_121/Docs/R4-2630011.zip).

For an implementation review, the useful questions are consequently specific: which alternatives must be provisioned before the switch, which candidate-cell reports remain available before activation, and which existing device capabilities cover the combined operation? The available sources do not supply a numerical interruption improvement. They do identify the dependencies that a credible improvement would have to satisfy. [RP-260232](https://www.3gpp.org/ftp/tsg_ran/TSG_RAN/TSGR_111/Docs/RP-260232.zip), [R4-2630009](https://www.3gpp.org/ftp/tsg_ran/WG4_Radio/TSGR4_121/Docs/R4-2630009.zip), [R4-2630011](https://www.3gpp.org/ftp/tsg_ran/WG4_Radio/TSGR4_121/Docs/R4-2630011.zip).

The October liaisons originated at RAN2's 12-16 October Jeju meeting and were forwarded to RAN4's 16-20 November Calgary meeting. Their detailed capability-agreement block is missing from the extraction. This analysis therefore follows the work-item objectives and the explicit requests, without claiming a final capability list or a November outcome. [R4-2630009](https://www.3gpp.org/ftp/tsg_ran/WG4_Radio/TSGR4_121/Docs/R4-2630009.zip).
